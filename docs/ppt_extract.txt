■트러블 슈팅 관리자 리뷰 삭제 승인 버튼 클릭 후 응답 없음구분 내용증상/오류[삭제 승인] 클릭 후 응답 없음 또는 장시간 대기해결 기록원인이슈 10과 같은 패턴 — 리뷰 DELETE + 평점 재계산 + 알림을 한 트랜잭션에 묶어 DB 락 발생해결 방법승인 핵심 처리만 짧은 트랜잭션, 평점·알림은 별도 트랜잭션 + 프론트 타임아웃후속 작업없음쿠폰 다운 시 예산·수량 미반영구분 내용증상/오류쿠폰 다운은 되는데 예산·수량이 즉시 안 줄거나, 소진 후에도 발급됨해결 기록원인ISSUED_QTY·ISSUED_BUDGET NULL일 때 UPDATE가 0건. INSERT 후 롤백 또는 소진 검증 누락해결 방법Mapper NVL(ISSUED_QTY,0)·NVL(ISSUED_BUDGET,0) 처리 + claimCoupon() INSERT 전 수량·예산 사전 검증후속 작업관리자 쿠폰 게시중/소진(EXHAUSTED) 탭 분리, 이벤트 탭 「쿠폰 소진」 UI 반영한 줄 요약 : 관리자 회원 삭제 승인에서다층(팝업/Ajax/DB) 이슈로 회원 탈퇴 운영 전체가 막힘「사업자 리뷰 삭제 요청을 관리자가 승인하는데, Ajax·DB 락 때문에 승인 버튼이 먹통이 됐습니다. 비동기 처리와 트랜잭션 분리로 해결했습니다.」한 줄 요약 : 쿠폰 예산/수량에서 쿠폰 발급/예산 집계가 조용히 틀어지는 데이터 무결성 문제「쿠폰 받기는 됐는데 발급 수량·예산이 DB에 안 찍혔습니다. Oracle에서 NULL+1=NULL이라 UPDATE가 실패한 거고, NVL로 0 처리해서 고쳤습니다.」■담당 역할 및 소감관리자회원관리커뮤니티 관리리뷰관리현황 파악재능나눔 승인FAQ/공지 CMS1:1문의관리배너 승인 및 관리사업자숙소 배너/쿠폰 신청쿠폰 승인 신청보유 쿠폰배너 승인 신청, 연동사용자이벤트/쿠폰 목록보유 쿠폰 노출·적용 쿠폰 다운, 소진 표시분실/보호 글 등록, 목록, 사진재능기부 글 목록, 상세유기동물 입양/목록 정보 조회커뮤니티 게시글, 댓글, 수정, 삭제, 좋아요, 신고수의사 상담 게시판 연동, 관리정지 회원 처리FAQ 공지 조회, 1:1 문의 등록

■향후 개선 과제구분내용현재개선결과기능 보완배너 만료 알림배너 종료일이 지나면 BannerExpiryScheduler와 조회 시점에 BannerExpiryService가 DB 상태만 ACTIVE → EXPIRED로 바꿉니다. 승인·반려·노출예정 때는 사업자 알림이 가지만, 만료될 때는 알림을 보내지 않습니다. 사업자는 배너 관리 화면을 직접 확인해야 기간 종료와 재신청 시점을 알 수 있습니다.만료 처리가 끝난 직후, 해당 사업자에게 만료 전용 알림을 TB_NOTIFICATION에 INSERT합니다. 기존 sendBannerApprovedNotification 등과 같은 방식으로 sendBannerExpiredNotification을 추가하고, 스케줄러·만료 API 호출 직후 연결합니다.사업자가 만료 당일(또는 자정 처리 후) 알림으로 기간 종료를 인지할 수 있고, 재신청 지연·광고 공백이 줄어듭니다. 「배너가 왜 안 보이지?」 같은 운영·1:1 문의도 감소할 수 있습니다.관리자 강제 탈퇴 → 탈퇴 이력 기록회원 자진 탈퇴는 STATUS_CD = WITHDRAWN 변경과 함께 TB_MEMBER_WITHDRAW에 기록되고, 7일 후 개인정보 삭제 스케줄(purgeExpiredWithdrawnMembers)이 돌아갑니다. 관리자 강제 탈퇴는 withdrawMember()에서 상태만 WITHDRAWN으로 바꾸고 탈퇴 이력 테이블에는 남기지 않습니다. 그래서 탈퇴 유형 구분과 7일 삭제 정책이 자진 탈퇴와 맞지 않을 수 있습니다.관리자 강제 탈퇴 시에도 insertMemberWithdraw를 호출하고, 탈퇴 유형을 ADMIN / MEMBER로 구분해 INSERT합니다. 이후 삭제 스케줄은 자진 탈퇴와 동일한 흐름을 타도록 맞춥니다.관리자·회원 탈퇴 모두 같은 보관·삭제 정책이 적용되고, 탈퇴 이력 추적이 가능해집니다. 「강제 탈퇴했는데 데이터가 남아 있다」 같은 정책 불일치를 줄일 수 있습니다.배너 통계 (클릭·노출)배너는 /api/banners로 노출되고, 클릭 시 linkUrl로 바로 이동합니다. 클릭 수·노출 수를 저장하거나 보여주는 기능은 없습니다. 사업자·관리자는 광고가 얼마나 효과가 있었는지 숫자로 확인할 수 없습니다.노출은 배너가 화면에 뜰 때 impression API/beacon으로, 클릭은 /api/banners/click/{id} → 카운트 후 redirect 방식으로 집계합니다. TB_BANNER_STAT 등에 저장하고, 관리자 CMS·사업자 배너 목록에 노출/클릭 수를 표시합니다.광고 효과를 수치로 확인할 수 있고, 재신청·기간 연장·위치 변경 등 운영·사업 결정 근거를 확보할 수 있습니다.보안·안정성로그인·권한 체크 통일 (Spring Security)/admin/**, /biz/**, 회원 전용 URL 접근을 Controller·Interceptor에서 세션 role을 각각 수동 확인합니다. (AdminBaseController, BizBaseController, SuspendedMemberInterceptor 등) 화면·API마다 방식이 조금씩 달라 체크 누락 시 보안 구멍이 생길 수 있고, 같은 로그인 검사 코드가 여러 곳에 중복됩니다.Spring Security로 URL 패턴별 역할을 한곳에서 정의합니다. 예: /admin/** → 관리자, /biz/** → 사업자. 기존 세션 로그인은 유지하되, 인증·인가는 필터 체인에서 전역 처리하고 Controller는 비즈니스 로직에 집중합니다.권한 누락 보안 리스크가 줄고, 신규 API 추가 시 설정만으로 보호할 수 있습니다. Controller 중복 코드 감소로 유지보수도 쉬워집니다.파일 업로드 검증 확대배너 업로드만 JPG/PNG/WebP 허용·PDF 차단 등 부분 검증이 있습니다. 커뮤니티·상품·분실신고·프로필 등 다른 업로드 경로는 검증 수준이 제각각이거나 약합니다. PDF·비이미지 파일이 올라가면 화면이 깨지거나 보안 이슈로 이어질 수 있습니다.공통 UploadValidator를 두고 모든 업로드 진입점에서 확장자·MIME(매직 바이트)·용량을 검사합니다. 배너 5MB, 상품·커뮤니티 등 유형별 화이트리스트를 한 모듈에서 관리하고, 저장 전에 반드시 통과시킵니다.잘못된 파일 업로드로 인한 화면 깨짐·보안 문제를 줄이고, 규칙을 한곳에서 통일해 신규 기능 추가 시 실수를 방지할 수 있습니다.설정·API 키 관리카카오 OAuth, 토스 결제, 택배 API, SMTP 등 민감 키가 application.properties에 평문으로 들어 있습니다. 로컬·운영 분리가 약하고, Git 공유·스크린샷·배포 시 키 노출 위험이 있습니다.application-local.yml / application-prod.yml로 환경 분리하고, 실제 키는 환경 변수(KAKAO_CLIENT_SECRET 등)로 주입합니다. local 설정·.env는 Git에서 제외하고, README에 필요 env 목록만 적습니다.저장소·팀 공유 시 API 키 유출 위험이 크게 줄고, 로컬·운영 설정 혼선을 방지합니다. 키 변경 시 코드 수정 없이 env만 바꿀 수 있습니다.에러 페이지 분리 (admin·biz)전역 ExHandler가 커뮤니티는 ?error=server로 보내고, 그 외는 error/500.jsp 정도만 씁니다. /admin/**, /biz/** 전용 에러 화면은 없어, 관리자·사업자 화면에서 오류가 나면 회원용 페이지를 보거나 홈으로 튕기는 혼란이 있을 수 있습니다. Ajax는 "error" 문자열만 와 원인 파악이 어렵습니다.요청 URI에 따라 admin 전용·biz 전용 500/403 JSP를 분리하고, Ajax/API는 JSON { code, message } 로 반환합니다. 레이아웃·「목록으로」 링크도 각 영역에 맞게 둡니다.운영자·사업자가 에러 후에도 같은 관리/사업자 영역에 머물고, 「갑자기 메인으로 간다」는 UX 혼란이 줄어듭니다. Ajax 디버깅·재현도 쉬워집니다.
